# Туториал по StructView

[English version](en.md) | [Обзор проекта](../README.ru.md)

Это пошаговое руководство показывает, как открывать, просматривать,
редактировать и сравнивать файлы структурированных данных в StructView, а
также пользоваться CLI. Названия пунктов меню ниже приведены на русском;
английский интерфейс можно выбрать в `Настройки -> Язык`
(`Settings -> Language`).

## 1. Установка и открытие документа

StructView читает и записывает JSON (`.json`), YAML (`.yaml`, `.yml`), TOML
(`.toml`) и JSON5 (`.json5`). Также приложение импортирует Graphviz DOT
(`.dot`, `.gv`), GraphML (`.graphml`) и GEXF (`.gexf`) как графы только для
чтения; их можно преобразовать в структурированные форматы. Для файлов сначала
используется известное расширение; при неизвестном расширении приложение
пытается определить формат по содержимому. Формат данных из стандартного ввода
также определяется по содержимому.

Для сборки нужны Rust с поддержкой Edition 2024 и Cargo:

```sh
cargo build --release
```

В Windows исполняемый файл находится в `target\release\struct_view.exe`, в
Linux и macOS — в `target/release/struct_view`.

Создайте файл `data.json` со следующим содержимым:

```json
{
  "service": "checkout",
  "enabled": true,
  "retries": 3,
  "users": [
    { "id": "u-1", "name": "Alice", "role": "admin" },
    { "id": "u-2", "name": "Bob", "role": "developer" }
  ],
  "tasks": [
    { "id": "task-1", "user_id": "u-1", "title": "Review release" },
    { "id": "task-2", "user_id": "u-2", "title": "Update tests" }
  ]
}
```

Откройте его из терминала. Если команда `struct_view` не добавлена в `PATH`,
запустите исполняемый файл из корневой папки проекта:

```sh
# Если struct_view доступна через PATH
struct_view data.json

# Windows
.\target\release\struct_view.exe data.json

# Linux или macOS
./target/release/struct_view data.json

# Во время разработки
cargo run -- data.json
```

Также файл можно открыть через `Файл -> Открыть…` или перетащить в окно
приложения. Запуск `struct_view` без имени файла открывает пустое окно.

## 2. Просмотр документа

В режиме дерева объекты и массивы отображаются как раскрываемые узлы.
Раскройте нужный узел, чтобы просмотреть его дочерние элементы. Кнопки дерева
позволяют раскрыть или свернуть документ целиком. Выберите узел, чтобы
взаимодействовать с ним или открыть его контекстное меню.

Переключатель представлений позволяет выбрать:

- **Дерево** — просмотр вложенной структуры документа.
- **Граф** — просмотр автоматически найденных или явно описанных связей.
  Поддерживаемые схемы и примеры перечислены в разделе
  [Форматы графов](#форматы-графов). Наведите курсор на сокращённую подпись
  связи, чтобы увидеть её целиком. Маршруты рассчитываются в фоне; во время
  расчёта отображается индикатор.
- **Таблица** — плоский список путей, значений и типов. Таблица учитывает
  активный фильтр поиска, её строки можно экспортировать в CSV.
- **Схема** — просмотр JSON Schema и компонентных/встроенных схем OpenAPI.
  Для обычного документа схема выводится из примера и не является
  формальным контрактом.

### Форматы графов

Представление графа распознаёт графовые структуры внутри документов JSON,
JSON5, YAML и TOML, а также импортирует отдельные файлы DOT, GraphML и GEXF.
GraphML и GEXF с расширением `.xml` определяются по корневому элементу.
Откройте документ и выберите **Вид → Граф**.

Файлы DOT, GraphML и GEXF доступны только для чтения. Импортёр преобразует их
в нормализованный документ `graph`/`nodes`/`edges`, сохраняя направление графа,
ID и подписи узлов, параллельные связи, веса и поддерживаемые атрибуты. Для
импортированных графов используется тип `directed_multigraph` или
`undirected_multigraph`, `bidirectional_multigraph` или `mixed_multigraph`,
чтобы не терять повторяющиеся связи; исключение —
strict DOT-графы с типом `directed` или `undirected`. Определения
ключей GraphML и атрибутов GEXF сохраняются в метаданных `graph`; остальные
XML-расширения — в `xml_extensions`.

Атрибуты графа, узлов и связей DOT сохраняются; цепочки рёбер раскрываются в
отдельные связи. Подграфы уплощаются для отображения; их ID, узлы и атрибуты
сохраняются в `graph.subgraphs`. Комментарии и исходное форматирование не
переносятся.
ID и атрибуты DOT в кавычках декодируются без внешних кавычек; escape-последовательности
подписей Graphviz, например `\n`, сохраняются. В strict-графах повторная связь
обновляет явно заданные атрибуты существующего ребра, а не создаёт параллельное
ребро и не применяет изменившиеся значения по умолчанию.

GraphML и GEXF должны содержать один граф. Смешанные направления сохраняются
для каждого ребра. Вложенные GraphML-графы
и гиперрёбра не поддерживаются. Внешние XML-декларации `DOCTYPE` игнорируются
без загрузки DTD; внутренние DTD-сущности не поддерживаются. Связи GEXF типа
`mutual` сохраняют стрелки с обеих сторон; временные и визуальные расширения
сохраняются как метаданные, но представление графа показывает статическую
структуру.

#### Направление каждого ребра и петли

Графы со списками рёбер поддерживают `direction: "directed"`, `"undirected"`,
`"bidirectional"` и `"reverse"`. Для обратного ребра исходные `source` и
`target` не меняются: стрелка направлена от цели к источнику.
Допустимы синонимы `forward`, `none`, `both`/`mutual`, `back`.
Поле `directed: true|false` у ребра задаёт направленную/ненаправленную связь.
Поддерживаются как `{"graph": {...}, "nodes": [...], "edges": [...]}`,
так и `{"graph": {"type": "...", "nodes": [...], "edges": [...]}}`.
Пути узлов сохраняют положение в исходном документе. Одновременное задание
узлов/рёбер в обоих местах отклоняется как неоднозначное.
`bidirectional: true` у ребра явно включает две стрелки, даже если
`graph.type` равен `undirected`. `false` оставляет направление по умолчанию
или переопределение `directed` без изменений. Поле должно быть boolean;
противоречие между явным `direction` и `bidirectional: true` вызывает ошибку.
Направление по умолчанию задаётся `graph.type`; `graph.direction` может его
переопределить. Добавлены типы `bidirectional`, `bidirectional_multigraph`,
`mixed`, `mixed_multigraph`. Для `mixed` неуказанное направление считается
`directed`. Неизвестное направление вызывает ошибку.

```json
{
  "graph": {"type": "mixed_multigraph"},
  "nodes": [{"id": "a"}, {"id": "b"}],
  "edges": [
    {"source": "a", "target": "b", "direction": "bidirectional"},
    {"source": "a", "target": "b", "direction": "reverse"},
    {"source": "a", "target": "b", "direction": "undirected"},
    {"source": "a", "target": "a", "direction": "directed"}
  ]
}
```

Те же поля работают в JSON5, YAML и TOML, включая вариант с `[nodes]`
и ключами узлов. В кортежах сущностей/связей направление можно указать
пятым элементом после источника, цели, подписи и кратности.
В парах долей — четвёртым после источника, цели и подписи.

DOT учитывает `dir=forward|back|both|none`, включая значения по умолчанию
и обновления атрибутов strict-рёбер. GraphML учитывает `directed` каждого
ребра. Стандарт GraphML не имеет двунаправленного типа: для переносимости
задайте две встречные направленные связи. StructView дополнительно понимает
строковый ключ `<data>` с именем `direction` для всех четырёх направлений.
GEXF учитывает `type` каждого ребра, включая стандартный `mutual`;
также допускаются расширения/синонимы `bidirectional` и `reverse`.

Петли сохраняются и прокладываются вне карточки узла, с отдельными портами
и трассами для параллельных петель. В списке смежности можно указать сам узел;
ненулевые диагональные веса матрицы создают петли, нулевые — нет.
Выведенные из данных ссылки на себя тоже отображаются.
Все направления и петли работают в GUI, подсказках и экспорте SVG/PNG.
Раскладка учитывает фактическое направление обратного ребра; двунаправленное
ребро соединяет узлы в обе стороны. Подписи обходят стрелки на обоих концах.
Списки смежности и матрицы скалярных весов также принимают направленные
и двунаправленные типы и `graph.direction`, включая обратное направление.
Для направленных/обратных матриц читается вся матрица; для ненаправленных
и двунаправленных — верхний треугольник вместе с диагональю.

### Поддерживаемые структуры графов

GUI и CLI используют одинаковые адаптеры для JSON, JSON5, YAML и TOML.
Поддерживаются следующие формы, а не произвольная сериализация любого графа:

- `nodes` вместе с `edges` или `links` в корне либо внутри `graph`.
  Узлы — записи с ID, строковые/целочисленные ID или словарь подписей/записей
  атрибутов. Ключ словаря становится ID; явный `id` должен совпадать с ключом.
  Концы рёбер задаются ID либо объектом с ID, а не индексом узла.
- NetworkX node-link (`directed`, `multigraph`, `nodes`, `links`/`edges`) и
  adjacency: массив массивов соседей в порядке `nodes`. Записи соседей
  используют `id` цели и могут содержать вес и `key` ребра.
  При корневых флагах NetworkX поле `graph` содержит произвольные атрибуты,
  а не вложенный граф/настройки. Зеркальные записи ненаправленной смежности
  объединяются; для мультиграфа нужны совпадающие ключи и веса рёбер.
- Cytoscape `elements: {nodes: [{data: {...}}], edges: [{data: {...}}]}`
  либо смешанный массив `elements: [{data: {...}}, ...]`.
  Рёбра могут идти раньше узлов. Узлу нужен `data.id`, ребру —
  `data.source` и `data.target`.
- Словари рёбер с ID в ключах и кортежи `[source, target]`,
  `[source, target, label_or_weight]`,
  `[source, target, label_or_weight, direction]`. Третий элемент также
  может быть объектом атрибутов с `weight`, `label`, `direction`.
  ID рёбер, ключи словаря и NetworkX `key` сохраняются в подписях.
- Явно обозначенная смежность: `{"graph":{"type":"directed"},
  "adjacency":{"a":["b"],"isolated":[]}}`. Соседи — ID или записи
  с `target`/`to`/`id`; поддерживаются и словари весов `"a":{"b":2}`.
  Без `nodes` собираются ID источников и целей; при явном списке узлов
  каждый конец ребра обязан присутствовать в нём.

Например, такой node-link документ работает без `graph.type`:

```json
{
  "directed": true,
  "multigraph": true,
  "nodes": ["a", "b"],
  "links": [
    ["a", "b", 2, "bidirectional"],
    ["b", "b", {"label": "loop", "direction": "reverse"}]
  ]
}
```

По умолчанию рёбра направленные. `graph.type` или булевый `directed`
задаёт направление по умолчанию, отдельное ребро может его переопределить.
Для одинаковых параллельных рёбер используйте `multigraph: true` либо
тип мультиграфа. Сохраняются изолированные узлы, петли, веса, подписи
и исходные пути узлов для поиска. При наведении на узел доступны все поля
исходной записи: например, `role`, вложенные объекты и элементы массивов,
булевы и пустые значения. Длинный список можно прокрутить в подсказке,
текст полей — выделить и скопировать. Для Cytoscape видны также поля
элемента вне `data`. При наведении на линию или подпись связи также видны
поля её исходной записи: дополнительные атрибуты, вложенные параметры
и пустые значения — под направлением и информацией о концах ребра.
Параллельные рёбра сохраняют собственные атрибуты; при объединении
дубликатов простого графа или зеркальных записей смежности в подсказке
сохраняются значения обеих записей.
Эти данные сохраняются и в подсказках узлов и рёбер SVG;
у PNG интерактивных подсказок нет. Размер карточек и раскладка не меняются.
Одного обычного поля `elements`, `nodes`
или `links` недостаточно для включения нового адаптера. Для пустых и
неоднозначных форм укажите явные флаги/тип графа.
Повторные ID узлов, неизвестные цели, конфликтующие псевдонимы концов рёбер,
неполные записи, неверные флаги/направления и конкурирующие контейнеры
вызывают ошибку, а не молчаливую потерю связей. Прежние структуры долей,
сущностей/отношений и матриц сохраняют поддержку.

Гиперрёбра, визуальные кластеры/вложенные подграфы и динамический GEXF
пока не реализованы. Для обычных нераспознанных документов остаётся
выведение связей; универсальная поддержка любой формы графа не гарантируется.

JSON команды CLI `graph` содержит `direction` каждого ребра и сводное
`direction` графа (`mixed`, если направления различаются).
Совместимое поле `directed` означает наличие хотя бы одной стрелки,
а не направление отдельного ребра. Конвертация в JSON/YAML/TOML/JSON5
сохраняет нормализованные направления.
XML-атрибуты с разными ключами, совпадающими по имени в результате импорта,
отклоняются вместо молчаливой потери данных. Явное значение может заменить
значение по умолчанию собственного ключа. Атрибуты GEXF `label` и `weight`
не должны конфликтовать с пользовательскими атрибутами того же имени.
Служебные метаданные `xml_attributes` и `xml_extensions` также не могут
перезаписывать одноимённые пользовательские значения: такой конфликт
отображается как ошибка импорта.

Преобразуйте импортированный граф через **Файл → Преобразовать в → JSON, YAML
или TOML** (также доступен JSON5). Исходный файл остаётся открытым и не
перезаписывается. CLI сохраняет такую же нормализованную структуру в новый
файл:

```sh
struct_view format network.graphml --output network.json
struct_view format network.dot --output network.yaml
```

Если форматировать графовый файл в stdout без `--output`, CLI выводит JSON.

Пример нормализованного представления:

```json
{
  "graph": {
    "type": "directed_multigraph",
    "source_format": "graphml",
    "name": "Сборка"
  },
  "nodes": [
    {"id": "compile", "label": "Компиляция", "attributes": {"kind": "задача"}},
    {"id": "test", "label": "Тесты", "attributes": {}}
  ],
  "edges": [
    {
      "source": "compile",
      "target": "test",
      "edge_id": "e1",
      "label": "выполняется перед",
      "weight": 0,
      "attributes": {"label": "выполняется перед", "weight": 0}
    }
  ]
}
```

При выборе YAML или TOML записывается та же структура.

#### Автоматически найденные связи сущностей

Объекты с полями `id`, `_id` или `$id` становятся узлами. Подпись берётся из
`name`, `title` или `label`, если такое поле есть. Ссылки создают поля вроде
`$ref`, `user_id`, `parent_id` и `depends_on`; значением может быть ID узла
или JSON Pointer, например `#/$defs/User`. Если ID неоднозначен из-за
дубликатов, связь не создаётся.

```json
{
  "services": [
    {"id": "api", "name": "API", "depends_on": ["db", "cache"]},
    {"id": "db", "name": "База данных"},
    {"id": "cache", "name": "Кэш"}
  ]
}
```

Объекты в JSON Schema `definitions`, `$defs` и `schemas` также считаются
сущностями, поэтому ссылки `$ref` между ними отображаются как связи.

#### Явные списки узлов и связей

Опишите объект с полями `graph`, `nodes` и `edges`. Узел — объект с полем
`id`, `_id` или `$id`; подпись задаётся полями `name`, `title` или `label`.
У связи должны быть `source` и `target` (или `from` и `to`). В подпись связи
могут попасть `label`, `name` или `relation`, вес `weight` или `value`, а
также `cardinality`, `contract` и ID связи. Единица из `graph.weight_unit`
добавляется к весу.

```json
{
  "graph": {
    "name": "Сборка",
    "type": "weighted_directed",
    "weight_unit": "мс"
  },
  "nodes": [
    {"id": "compile", "label": "Компиляция"},
    {"id": "test", "label": "Тесты"}
  ],
  "edges": [
    {"source": "compile", "target": "test", "relation": "перед", "weight": 120}
  ]
}
```

Допустимые значения `graph.type`: `directed`, `weighted_directed`,
`undirected`, `weighted_undirected`, `directed_multigraph` и
`undirected_multigraph`. Мультиграфы сохраняют параллельные связи, в том числе
с одинаковыми концами.

#### Неориентированный список смежности

Укажите `graph.type = "undirected"` и объект `adjacency`: его ключи — узлы,
массивы значений — их соседи. Узел, указанный только как сосед, тоже будет
добавлен. Симметричные записи одной связи объединяются.

```json
{
  "graph": {"type": "undirected"},
  "adjacency": {
    "anna": ["boris"],
    "boris": ["anna"],
    "isolated": []
  }
}
```

#### Взвешенная неориентированная матрица смежности

Укажите `graph.type = "weighted_undirected"`, порядок узлов в `node_order` и
квадратную симметричную `adjacency_matrix` в этом порядке. Приложение читает
верхний треугольник матрицы и игнорирует диагональ. Любое числовое значение,
включая `0`, означает вес существующей связи; `null` означает отсутствие
связи. Поэтому связь с нулевым весом отличается от отсутствующей.

```yaml
graph:
  type: weighted_undirected
  weight_unit: км
  node_order: [A, B, C]
  adjacency_matrix:
    - [0, 12, null]
    - [12, 0, 0]
    - [null, 0, 0]
```

В примере есть связи `A—B` весом `12 км` и `B—C` весом `0 км`; связи `A—C`
нет.

#### TOML-каталог сущностей и отношений

Для именованных сущностей и подписанных отношений задайте все четыре поля
метаданных, показанные ниже. `edges` содержит кортежи
`[ID_источника, ID_цели, подпись, кратность?]`. Для неориентированных
отношений укажите `directed = false`.

```toml
[graph]
name = "Магазин"
directed = true
entity_count = 2
relation_count = 1

[entities]
customer = "Покупатель"
order = "Заказ"

[relations]
edges = [["customer", "order", "оформляет", "1:N"]]
```

#### Двудольные и многодольные графы

Перечислите не менее двух именованных долей — массивов ID узлов — и укажите
связи между ними в `[relations].pairs`. Пара может соединять любые две разные
доли; связи внутри одной доли игнорируются. ID должны быть уникальны среди
всех долей. Для двух долей укажите `type = "bipartite"`, для двух или более —
`type = "multipartite"`. Каждая доля отображается отдельной колонкой.
`directed` необязателен и по умолчанию равен `false`.

```toml
[graph]
type = "multipartite"
directed = false

[partitions]
people = ["ada"]
projects = ["compiler"]
organizations = ["lab"]

[labels]
ada = "Ада"
compiler = "Компилятор"
lab = "Исследовательская лаборатория"

[relations]
pairs = [
  ["ada", "compiler", "пишет"],
  ["compiler", "lab", "принадлежит"],
]
```

#### TOML-мультиграфы

Таблица `[nodes]` сопоставляет ID узлов с подписями, а отдельная таблица
`[[edges]]` описывает каждую связь. Для `graph.type` укажите
`directed_multigraph` или `undirected_multigraph`. Параллельные связи
сохраняются; в записи связи доступны те же поля концов и подписи, что и в
явном списке узлов и связей.

```toml
[graph]
type = "directed_multigraph"

[nodes]
api = "API"
database = "База данных"

[[edges]]
source = "api"
target = "database"
relation = "читает"

[[edges]]
source = "api"
target = "database"
relation = "записывает"
```

## 3. Поиск ключа, значения или пути

Откройте окно поиска кнопкой на панели инструментов или сочетанием `Ctrl+F`
(`Cmd+F` в macOS). Введите запрос, выберите область поиска — ключи, значения
или пути — и при необходимости включите учёт регистра, точное совпадение,
совпадение целого слова или регулярное выражение. Переключайтесь между
результатами кнопками «Назад»/«Вперёд» или выберите путь результата, чтобы
найти узел в документе. Окно поиска сначала открывается внутри главного окна.
Чтобы отделить его, нажмите кнопку меню с тремя точками в верхней части окна
и выберите `Отделить окно`.
Чтобы встроить его обратно, нажмите `Прикрепить окно` в верхней части отдельного
окна. То же относится к диалогам добавления и редактирования полей.

В примере выше запрос `Alice` найдёт значение. Чтобы найти ключ `id`,
выберите поиск по ключам и точное совпадение. Конструктор регулярных
выражений умеет добавлять экранированный текст и распространённые фрагменты
шаблонов. Используется синтаксис регулярных выражений Rust.

## 4. Редактирование и сохранение

Переключитесь в режим **Редактирование**. В контекстном меню узла выберите
`Редактировать поле…`, чтобы изменить значение или тип; ключ объекта также
можно переименовать. Добавляйте поля объектов и элементы массивов через
кнопку `+` рядом с объектом или массивом: конструктор позволяет вручную ввести
имя и выбрать тип поля. Строки вводятся обычным текстом, числа и логические
значения проходят проверку, а новые объекты и массивы создаются пустыми.
Заполняйте вложенные структуры таким же способом через `+` у нужного узла.
Формат TOML не поддерживает `null`, поэтому это значение недоступно при
редактировании TOML.

Чтобы создать документ с нуля, выберите `Файл -> Создать файл…`, укажите имя
с поддерживаемым расширением и добавляйте поля в новый пустой объект кнопкой
`+` рядом с ним.
Доступны отмена и повтор до 100 изменений документа (`Ctrl+Z` / `Ctrl+Y`;
в macOS — `Cmd+Z` / `Cmd+Shift+Z`).

Сохраните изменения командами меню `Файл`. Формат при сохранении выбирается
по расширению целевого файла; если расширение не поддерживается, используется
формат открытого документа. Для явного преобразования выберите
`Файл -> Преобразовать в` и укажите целевой формат. Результат записывается в
отдельный файл, а открытый документ остаётся без изменений.

Выберите одну или несколько структур и скопируйте их через
`Правка -> Копировать` или `Ctrl+C`/`Cmd+C`. Их можно вставить в выбранный
объект или массив другого открытого документа через `Правка -> Вставить` или
`Ctrl+V`/`Cmd+V`. Вставка изменяет документ в памяти; чтобы записать изменения
на диск, сохраните файл.

## 5. Сравнение файлов

Выберите `Файл -> Сравнить файлы…` и укажите два или более файла. Таблица
показывает изменённые пути относительно первого файла. Объекты и массивы
сравниваются рекурсивно; отсутствующий путь отличается от значения `null`.
Переключитесь на парный diff, чтобы изучить выбранную пару. Если файлов
больше двух, укажите нужные версии в списках выбора над diff.

Сразу открыть несколько файлов в режиме сравнения можно и из терминала:

```sh
struct_view before.json after.yaml
```

Сравнение доступно только для чтения. Чтобы вернуться к обычному документу,
используйте `Файл -> Открыть…` или `Файл -> Закрыть файл`.

## 6. Командная строка

CLI выполняет команды без запуска графического интерфейса. При разработке
добавляйте к примерам `cargo run --`; в остальных случаях используйте
исполняемый файл релизной сборки или команду `struct_view`, доступную через
`PATH`. Команды, параметры и сообщения CLI выводятся на английском языке.

Проверить синтаксис файла и определить его формат:

```sh
struct_view validate data.json
```

Отформатировать файл, записать результат в другой файл или вывести его без
отступов:

```sh
struct_view format data.json --output normalized.json
struct_view format data.json --minify
```

Если указан `--output`, формат выбирается по расширению выходного файла. Если
расширение не поддерживается, используется формат входного файла. Без
`--output` сохраняется исходный формат.

Найти значение, ключ или путь:

```sh
struct_view find Alice data.json
struct_view find --keys --exact id data.json
struct_view find --paths --regex '^users\.[0-9]+\.name$' data.json
```

Запрос в форме `ключ: значение` ищет совпадение имени поля и его значения в
одном узле:

```sh
struct_view find 'name: Alice' data.json
```

Параметр `--regex` нельзя использовать вместе с `--exact` или
`--whole-word`. Для регулярного выражения по-прежнему можно включить учёт
регистра.

Сравнить два или более файла и вывести изменённые пути:

```sh
struct_view diff before.json after.json
```

Команда `compare` является псевдонимом `diff`. Укажите `-` вместо одного из
файлов, чтобы прочитать этот источник из стандартного ввода. Например, в
оболочках с перенаправлением ввода:

```sh
struct_view validate - < data.yaml
```

Список всех команд и параметров показывает `--help`.

Код возврата `0` означает успешное выполнение, `1` — ошибку данных или
ввода-вывода, отсутствие результатов поиска либо найденные различия в
`diff`, `2` — ошибку разбора аргументов. Поэтому код `1` у `diff` может
означать, что сравнение прошло успешно и файлы различаются.

## 7. Особенности форматов и производительность

- GUI загружает документ целиком и хранит разобранное дерево в памяти.
  Виртуализация строк уменьшает затраты на отрисовку раскрытого дерева, но
  расход памяти всё равно растёт вместе с числом узлов. Для очень больших
  документов оставляйте ненужные ветки свёрнутыми или используйте CLI.
- В TOML нет значения `null`. Даты и время TOML сохраняют собственный тип
  при сохранении в TOML и становятся строками при преобразовании в
  JSON-совместимые форматы.
- Нестрочные ключи YAML сохраняются при записи в YAML. Их преобразование в
  JSON или TOML отклоняется, чтобы не менять типы ключей.
- Комментарии JSON5, YAML и TOML могут сохраняться при записи в формат,
  который их поддерживает, но исходные расположение и стиль не сохраняются.
  Комментарии нормализуются в отдельные строки в начале файла; строгий JSON
  комментарии не поддерживает.

Полный список возможностей и дополнительные сведения о форматах приведены в
[основном README](../README.ru.md).
